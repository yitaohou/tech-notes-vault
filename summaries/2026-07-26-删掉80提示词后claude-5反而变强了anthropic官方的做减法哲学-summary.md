## 一句话总结

Anthropic 把 Claude Code 系统提示词砍掉超过 80%（[00:00]），却在内部编码评估中没测出性能下降（[00:00]），核心原因是：模型能力变强后，旧时代『保姆式』的详细提示词从帮手变成了枷锁，[[verbose-prompt-paradigm|越写越细的提示词范式]]正在被[[progressive-disclosure|按需加载]]和[[interface-design-over-prompting|接口设计优先]]的[[context-engineering|Context Engineering]]取代。

## 核心内容

### 从代码补全到上下文生态：提示词理念是怎么一步步演化的

视频先梳理了一条演化脉络（[00:00]）：最早的 [[copilot-code-completion|Copilot]] 只是单纯的代码补全工具，上下文仅限当前文件和相邻文件；到了 [[cursor-editor|Cursor]]，整个代码库被索引，检索出的相关片段喂给模型，上下文扩展到项目级别；再到 [[chat-based-coding-context|ChatGPT 和早期 Claude]] 时代，开发者用对话方式写代码，上下文变成了对话历史。而到 Opus 5、Sonnet 5 配合 Claude Code 这种 Agent 级别，上下文的定义被再次刷新——不再是文本堆砌，而是包含系统提示词、动态技能、本地配置、[[automatic-memory-claude|自动记忆]]和[[rich-context-references|丰富引用]]的复杂生态系统，这就是 [[context-ecosystem-claude-code|Claude Code 的上下文生态]]。Anthropic 把管理这整套生态的过程称为 [[context-engineering|Context Engineering]]。

而在此之前，行业主流做法是 [[verbose-prompt-paradigm|详细提示词范式]]：从 GPT-3 时代起就流行把提示词写得越细越好，把 AI 当成听不懂人话的实习生手把手教（[00:00]）。但 Anthropic 工程师发现，太多无关上下文会造成 [[context-dilution|注意力稀释]]，过去的保姆式提示词反而限制了模型发挥（[00:00]），这就是 [[hardcoded-prompt-rules-limitation|硬编码规则的局限]]：模型变强后，旧时代为约束行为写的硬性规则开始限制模型自身判断。

### 这次瘦身具体删了什么

Anthropic 工程师 [[thariq-shihipar|Thariq Shihipar]] 把这次 [[system-prompt-reduction-claude-code|系统提示词精简]]的原因总结为几个核心转变（[00:00]）。需要强调的是，删掉的是大量示例、重复指令和过度绝对的限制，安全规则并未被删（[00:00]）。

一个典型例子是代码风格规则。旧版提示词里有 [[hard-coded-prompt-rules|硬性规则]]，比如"默认不写注释""最多只能写一行简短注释"，试图堵死所有边界条件，但这在遇到复杂算法或用户自有代码规范时会导致代码难以维护（[03:01]）。新版只用一句 [[code-style-matching-instruction|"编写与周围代码风格一致的代码"]]取代了这些硬规则，让模型自行匹配注释密度、命名和惯用语法（[03:01]）——这说明新模型已具备类似高级工程师的上下文感知能力。而且硬性规则还容易引发 [[conflicting-instructions-problem|指令冲突问题]]：当系统提示词说"不要写注释"、用户又要求"留下适当文档"时，模型会因自相矛盾而困惑（[03:01]）。另外，同一条要求不必在系统提示词和工具描述里反复强调，这是 [[avoid-redundant-instructions|避免冗余指令]]的原则（[03:01]），而且哪怕新模型拥有百万 token 级[[context-window-limits-large-models|超大上下文窗口]]，塞入无关信息依然会干扰注意力、推高 token 成本（[03:01]）。

### 工具调用：从 few-shot 示例到接口设计

以前教 AI 用工具的稳妥方法是 [[few-shot-prompting-tool-use|喂大量 few-shot 示例]]，逐一说明每种场景的输入格式（[03:01]）。但对新模型而言，[[few-shot-examples-limit-exploration|示例反而会限制探索空间]]：如果示例只展示基础用法，模型可能永远学不会组合使用高级参数（[03:01]）。不过视频特别提醒，这一判断仅针对新模型，老模型仍然需要 few-shot 示例，并非所有工具都不该给例子（[03:01]）。

取而代之的最佳实践是 [[interface-design-over-prompting|设计更好的工具接口]]，而不是写长篇说明（[03:01]）。例如 Todo 工具用 [[enum-parameter-design|枚举参数设计]]，把状态定义为 pending、inprogress、completed 三个值，模型看到枚举就能自己理解调用方式，只需再加一句"保持只有一个任务处于 in_progress"这样的简短说明即可（[03:01]）。这背后的理念是 [[api-design-as-documentation|API 设计本身就是最好的文档]]：与其花几百字解释一个糟糕接口，不如把输入输出结构设计得更清晰（[03:01]）。

### 按需加载：渐进式披露如何重塑 Agent 架构

视频认为，从"全盘托出"转向"按需加载"是这次理念转变中对开发 AI Agent 影响最大的一点，即 [[progressive-disclosure|渐进式披露]]（[03:01]）。具体做法是把代码审查规则、数据库迁移注意事项等分别写成独立的 Skill，模型只在真正需要执行相应任务时才调用对应 Skill 读取规则，而不是把所有规则塞进主提示词（[06:01]）。工具定义也可以按需加载：Agent 起初只知道有这个工具存在，真正需要时才加载具体定义，类似主函数保持干净、业务逻辑封装进模块按需调用的 [[on-demand-tool-loading|按需工具加载]]思路（[06:01]）。

这也带来了记忆机制的变化。早期官方建议开发者手动把经验教训记进 [[claude-md-file|CLAUDE.md 文件]]，如同带实习生每次犯错都要手动记小本子（[06:01]）；而现在 [[automatic-memory-claude|Claude 能自动记忆]]，在工作过程中自动总结经验并保存，下次自动调取，开发者不用再手动记录（[06:01]）。但 CLAUDE.md 并非完全没用，好的做法是只保留模型无法通过扫描代码库自行获知的核心信息，比如项目陷阱，不写模型扫一眼就懂的废话（[09:55]）。

### 提示词瘦身 ≠ 放弃提示工程，而是升级为 Context Engineering

视频强调，系统提示词大幅精简不代表 Anthropic 放弃了 [[prompt-engineering|Prompt Engineering]]，而是再次强调了范畴更大的 [[context-engineering|Context Engineering]]（这一概念至少从 2025 年就被系统性提出，并非新词）（[06:01]）。提示词只是对 AI 说的一句话，而上下文是 AI 做决策所依赖的全部背景信息，二者范畴不同（[06:01]）。新模型生成代码出 bug，很多时候不是模型能力不够，而是给的上下文不对——参考资料混乱、项目边界不清、该给的信息没给（[06:01]）。

好的上下文应当是 [[rich-context-references|丰富且高保真的引用]]：可以把完整测试套件直接交给模型，让它照着测试用例实现功能，而不只是给文字规范；新模型也能直接处理 HTML 格式的 UI 原型作为参考，比几百字描述界面效果更好（[06:01]）。此外还可以用 [[rubrics-evaluation|Rubrics 评估机制]]，启动专门的验证 Agent，把 Rubrics（如什么样的 API 设计才算优雅）喂给它，评估主 Agent 写出的代码是否达标（[06:01]）。

不过裸用顶配模型处理复杂项目也有现实成本问题：[[claude-5|Claude 5]] 的输出价格约是 Opus 4.5 的两倍，如果每次都塞入大量无关代码和资料，账单会迅速变得难看（[06:01]）。

### 安全机制与成本控制：模型分流的工程实践

[[claude-5|Claude 5]] 配有额外的[[safety-classifier-claude|安全分类器]]，用于识别涉及网络安全或生物安全的敏感请求（[09:02]）。部分命中的请求可能被转交给 Opus 处理，在 API 场景下也可能被直接拒绝（[09:02]）；Anthropic 称该机制平均在不到 5% 的会话中触发（[09:20]），但存在误伤风险，正常开发任务也可能被误判，因此正式接入前必须先实测（[09:25]）。

在成本控制上，常见工程做法是 [[model-routing-by-complexity|按任务复杂度做模型分流]]：简单补全和基础问答用小模型，跨多文件、需要长程推理的硬核重构才调用顶配模型（[09:02]）。视频特别说明，这并非官方规定的固定架构，而是通用成本控制思路，具体分流方式需要根据自身业务量调整（[09:02]）。

### 范式转移：开发者的角色正在从"写提示词"变成"设计系统"

视频认为早期行业里流行的观点是，写好 Prompt 是一门需要学习各种"咒语"的玄学，甚至催生了"提示词工程师"这一岗位（[09:40]）。但随着模型推理能力进化，[[prompt-engineering|Prompt Engineering]] 正在向 [[context-engineering|Context Engineering]] 演进，本质上是向传统软件工程思维的回归（[09:45]）：工具接口要自解释、参数命名清晰类型准确（[10:05]），大段规范要拆分成按需加载的模块而非一次性塞给模型（这正是 [[progressive-disclosure|渐进式披露]]思路的具体应用，[10:10]），参考资料要尽量提供高保真代码和测试用例而非模糊文字描述，这比抠提示词字眼有用得多（[10:15]）。

视频最后提出 [[paradigm-shift-human-designs-context|范式转移]]的判断：未来 AI 编程考验的不是聊天技巧，而是对系统架构的理解，以及能否为 AI 构建清晰、高效、无歧义的工作环境（[10:25]）；模型会越来越像有经验的架构师，不需要被教怎么写 for 循环，而是需要清晰的项目边界、高质量参考实现和合理工具链（[10:35]）。这意味着开发门槛提高，只会写简单 Prompt 的"提示词工程师"可能逐渐失去优势，真正懂系统架构和高效上下文构建的开发者才能最大化发挥顶级模型价值（[10:45]）。这场转移继承了软件工程中模块化、接口设计、关注点分离的传统，但颠覆了代码产出方式：AI 不再是打字机，而是工程伙伴（[10:55]）。
